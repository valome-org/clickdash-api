# Database Migrations Guide

This guide explains how to manage database schema changes using Alembic migrations.

## Overview

Alembic is a database migration tool that allows you to:
- Track database schema changes
- Apply changes safely across environments
- Roll back changes if needed
- Generate migrations automatically

## Setup (Already Done)

Alembic has been initialized and configured for this project. The configuration includes:
- `alembic/` directory with migration files
- `alembic.ini` configuration file
- Automatic model detection from `database/models.py`

## Common Migration Commands

### 1. Check Current Migration Status
```bash
alembic current
```

### 2. Create a New Migration

#### Auto-generate migration (recommended)
```bash
alembic revision --autogenerate -m "Description of changes"
```

#### Manual migration
```bash
alembic revision -m "Description of changes"
```

### 3. Apply Migrations
```bash
# Apply all pending migrations
alembic upgrade head

# Apply to specific revision
alembic upgrade <revision_id>

# Apply one migration at a time
alembic upgrade +1
```

### 4. Rollback Migrations
```bash
# Rollback one migration
alembic downgrade -1

# Rollback to specific revision
alembic downgrade <revision_id>

# Rollback all migrations
alembic downgrade base
```

### 5. View Migration History
```bash
# Show current and available revisions
alembic history

# Show verbose history
alembic history --verbose
```

## How to Add a New Table

### Step 1: Create the Model
Add your new model to `database/models.py`:

```python
class NewTable(Base):
    __tablename__ = "new_table"

    id = Column(Integer, primary_key=True, index=True)
    name = Column(String, nullable=False)
    created_at = Column(DateTime(timezone=True), server_default=func.now())
```

### Step 2: Generate Migration
```bash
alembic revision --autogenerate -m "Add new_table"
```

### Step 3: Review Migration File
Check the generated migration file in `alembic/versions/` and verify it's correct.

### Step 4: Apply Migration
```bash
alembic upgrade head
```

## How to Modify Existing Tables

### Adding a Column
1. Add the column to your model in `models.py`
2. Generate migration: `alembic revision --autogenerate -m "Add column_name to table_name"`
3. Apply: `alembic upgrade head`

### Removing a Column
1. Remove the column from your model
2. Generate migration: `alembic revision --autogenerate -m "Remove column_name from table_name"`
3. Apply: `alembic upgrade head`

### Changing Column Type
1. Modify the column type in your model
2. Generate migration: `alembic revision --autogenerate -m "Change column_name type in table_name"`
3. Review the generated migration carefully
4. Apply: `alembic upgrade head`

## Example: Adding a User Table

This example shows how we added the User table:

### 1. Added Model to `database/models.py`:
```python
class User(Base):
    __tablename__ = "users"

    id = Column(Integer, primary_key=True, index=True)
    user_id = Column(String, unique=True, index=True, nullable=False)
    email = Column(String, unique=True, index=True, nullable=False)
    username = Column(String, unique=True, index=True, nullable=False)
    full_name = Column(String, nullable=True)
    is_active = Column(Boolean, default=True, nullable=False)
    is_admin = Column(Boolean, default=False, nullable=False)
    created_at = Column(DateTime(timezone=True), server_default=func.now())
    updated_at = Column(DateTime(timezone=True), onupdate=func.now())
```

### 2. Generated Migration:
```bash
alembic revision --autogenerate -m "Add users table"
```

### 3. Applied Migration:
```bash
alembic upgrade head
```

## Migration File Structure

Migration files are located in `alembic/versions/` and contain:
- `upgrade()` function: applies the changes
- `downgrade()` function: reverts the changes

Example migration file:
```python
def upgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.create_table('users',
    sa.Column('id', sa.Integer(), nullable=False),
    sa.Column('user_id', sa.String(), nullable=False),
    sa.Column('email', sa.String(), nullable=False),
    # ... more columns
    sa.PrimaryKeyConstraint('id')
    )
    # ### end Alembic commands ###

def downgrade() -> None:
    # ### commands auto generated by Alembic - please adjust! ###
    op.drop_table('users')
    # ### end Alembic commands ###
```

## Best Practices

### 1. Always Review Generated Migrations
- Check the generated SQL is correct
- Ensure data won't be lost
- Add custom logic if needed

### 2. Backup Before Major Changes
```bash
pg_dump clickdash_db > backup_$(date +%Y%m%d_%H%M%S).sql
```

### 3. Test Migrations
- Test in development first
- Verify both upgrade and downgrade work
- Check data integrity after migration

### 4. Use Descriptive Messages
```bash
# Good
alembic revision --autogenerate -m "Add user authentication tables"

# Bad
alembic revision --autogenerate -m "changes"
```

### 5. Handle Data Migrations
For complex data changes, create manual migrations:

```python
def upgrade() -> None:
    # Schema changes
    op.add_column('users', sa.Column('full_name', sa.String(), nullable=True))

    # Data migration
    connection = op.get_bind()
    connection.execute("UPDATE users SET full_name = first_name || ' ' || last_name")

def downgrade() -> None:
    op.drop_column('users', 'full_name')
```

## Troubleshooting

### Migration Conflicts
If you have conflicting migrations:
```bash
alembic merge <rev1> <rev2> -m "Merge conflicting migrations"
```

### Reset Migrations (Development Only)
```bash
# Drop all tables
alembic downgrade base
# Recreate from scratch
alembic upgrade head
```

### Check SQL Without Applying
```bash
alembic upgrade head --sql
```

## Production Deployment

### 1. Run Migrations Before Deploying Code
```bash
alembic upgrade head
```

### 2. Use Transaction Wrapping
Alembic runs migrations in transactions by default, but be careful with:
- Large data migrations
- Schema changes that might lock tables

### 3. Monitor Migration Performance
```bash
# Time the migration
time alembic upgrade head
```

## Environment-Specific Considerations

### Development
- Feel free to reset and recreate migrations
- Test both upgrade and downgrade paths

### Staging
- Should mirror production process
- Test migrations with production-like data

### Production
- Always backup before migrations
- Run during maintenance windows for major changes
- Monitor application during and after migration
